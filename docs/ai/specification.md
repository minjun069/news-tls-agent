# AI 기능 명세서 — news-tls-agent

관련 PRD: [`REQUIREMENTS.md`](../REQUIREMENTS.md) · 기술 설계서: [`TECH_DESIGN.md`](../architecture/overview.md)

AI 기능은 둘이다. **타임라인 생성 파이프라인**(LLM 호출 9종)과 **이슈 질의 에이전트**(도구 호출 기반). 성격이 달라 따로 명세한다.

## 1. 공통

### 1.1 모델

| 용도 | 모델 | 선택 근거 |
|---|---|---|
| 파이프라인 전 단계 | `gemini-2.5-flash` | 긴 입력(기사 다수)을 처리해야 하고 호출이 잦다 |
| 질의 에이전트 | `gemini-2.5-flash` | 도구 호출 지원. 단일 provider로 설정 단순화 |
| 임베딩 | `text-embedding-004` | API 호출이라 GPU 불필요 |

> provider가 Google로 고정된 것은 보유 API 키에 따른 **제약**이다. 기술적 우위 판단이 아니다.

### 1.2 출력 형식

구조화된 출력이 필요한 모든 호출은 **구조화 출력(response schema)** 을 사용하고, 받은 결과를 Pydantic으로 다시 검증한다.

- 구조화 출력이 스키마 준수를 API 수준에서 강제한다
- Pydantic 검증은 값 범위·형식(날짜, ID 타입)을 잡는다
- 남는 실패는 타임아웃·빈 응답·안전필터 차단이다 (EX-03)

### 1.3 비용 통제

| 항목 | 방식 |
|---|---|
| 수집 루프 | 종료 조건 4가지로 라운드를 제한 ([타임라인 종료 정책](../requirements/timeline.md#수집-루프-종료-정책)) |
| 적합성 판정 | 배치 처리. 건당 호출하지 않는다 |
| 중복 생성 | 동일 토픽은 기존 이슈 재사용 (ISS-003) |
| 엔티티 추출 | 기사 단위 저장. 같은 기사는 1회만 추출 |
| 임베딩 | 적재 시 1회. 검색 시에는 쿼리만 임베딩 |

## 2. 타임라인 생성 파이프라인

### 2.1 호출 목록

| # | 단계 | 입력 | 출력 | 반복 |
|---|---|---|---|---|
| P1 | 질의 의도 해석 | 토픽 문자열 | 해석된 의도, 되묻기 필요 여부 | 되묻기당 1회 |
| P2 | 가상 타임라인 생성 | 해석된 의도 | 기간, 가상 이벤트 목록 | 1회 |
| P3 | 검색 쿼리 생성 | 가상 이벤트 / 선후 이벤트 | 검색 방식, 키워드 조합 또는 문장 | 라운드당 1회 |
| P4 | 핵심 이벤트 선정 | 검색 결과 기사 배치 | 적합 기사 ID 목록, 기사–이벤트 대응 | 라운드당 1회 |
| P5 | 선후 이벤트 추출 | 선정된 기사 본문 | 선후 이벤트 목록(시점, 내용) | 라운드당 1회 |
| P6 | 충분성 검토 | 선정된 이벤트 전체, 가상 타임라인 | 충분 여부, 부족한 지점, 갱신된 기간 | 라운드당 1회 |
| P7 | 가상 이벤트 생성 | 부족한 지점 | 추가 가상 이벤트 | 부족 판정 시 1회 |
| P8 | 타임라인 병합 | 선정된 기사와 대응 정보 | 제목, 요약, 이벤트 목록 | 1회 |
| P9 | 엔티티·관계 추출 | 기사 본문 1건 | 엔티티, 관계 | 미추출 기사당 1회 |

### 2.2 P1 · 질의 의도 해석

**목적**: 토픽 문자열에서 무엇에 대한 타임라인을 원하는지 특정한다.

**출력**
- 해석된 의도 (사건 범위, 관점)
- 되묻기 필요 여부와 되물을 내용

**지시 요점**
- 사건을 특정할 수 없으면 되묻는다. 임의로 좁히지 않는다
- 되묻는 질문은 하나만 한다. 여러 개를 나열하지 않는다
- 되묻기 횟수가 상한에 도달하면 해석된 의도로 진행한다 ([PRD 공통 리스크](../REQUIREMENTS.md#7-공통-리스크))

### 2.3 P2 · 가상 타임라인 생성

**목적**: 무엇을 찾아야 하는지 먼저 그린다. 검색 쿼리의 품질이 여기서 결정된다.

**출력**
- 타임라인 기간 (시작일, 종료일)
- 가상 이벤트 목록 (예상 시점, 예상 내용)

**지시 요점**
- 기간은 사건의 성격에서 추정한다. 근거 없이 넓게 잡지 않는다
- 가상 이벤트는 **검색을 이끌기 위한 가설**이다. 사실로 단정하는 표현을 쓰지 않는다

> **가상 타임라인은 HyDE(Hypothetical Document Embeddings)의 타임라인판이다.** 질의를 그대로 검색하는 대신, 찾을 것으로 기대되는 문서를 먼저 생성해 그것으로 검색한다. 뉴스처럼 질의와 본문의 표현이 크게 다른 도메인에서 효과가 크다.

### 2.4 P3 · 검색 쿼리 생성

**목적**: 가상 이벤트 또는 선후 이벤트를 검색 가능한 형태로 바꾼다.

**출력**
- 검색 방식 (키워드 / 의미 / 결합)
- 키워드 조합(OR / AND) 또는 검색용 문장
- 기간 필터 범위

**지시 요점**
- 고유명사·날짜·수치가 핵심이면 키워드 검색을 고른다
- 개념·상황 서술이 핵심이면 의미 검색을 고른다
- 판단이 서면 결합 검색을 고른다
- **선택한 방식과 이유를 함께 반환한다.** 로그에 남긴다 (NFR-14)

관련 결정: [ADR-0003](../decisions/0003-search-strategies.md)

### 2.5 P4 · 핵심 이벤트 선정

**목적**: 검색 결과 중 타임라인에 실제로 속하는 기사를 고른다. **정밀도(precision) 담당.**

**입력 형식** — 기사를 배치로 넣는다

```
ARTICLE_ID: {id}
SERVICE_DATE: {YYYY-MM-DD}
TITLE: {제목}
CONTENT: {본문}
```

**출력**
- 적합 기사 ID 목록
- 기사별 대응 이벤트 (시점, 내용 요약)
- 탈락 기사 ID와 탈락 사유

**지시 요점**
- 입력 목록에 있는 `ARTICLE_ID`만 사용한다
- 주제가 겹치더라도 이 타임라인의 사건이 아니면 제외한다
- 같은 사건을 다룬 기사가 여럿이면 모두 적합으로 표시한다. 중복 제거는 병합 단계에서 한다
- **기사–이벤트 대응을 반드시 함께 반환한다.** 병합 단계에서 재계산하지 않는다

> 탈락 사유를 받는 이유는 다음 라운드의 쿼리 생성에 쓰기 위해서다. "A 때문에 탈락했으니 B를 찾아라"가 가능해진다.

### 2.6 P5 · 선후 이벤트 추출

**목적**: 선정된 기사 본문에 **서술된** 선행·후속 사건을 찾아낸다. 다음 라운드의 검색 씨앗이 된다.

**출력**
- 선후 이벤트 목록 (시점, 내용, 출처 기사 ID)

**지시 요점**
- 기사에 **실제로 서술된** 사건만 추출한다. 추론하지 않는다
- 가상 타임라인 기간을 벗어나는 사건은 제외한다
- 이미 선정된 이벤트와 같은 사건이면 제외한다

> 이 단계가 이 파이프라인의 핵심이다. 뉴스 기사에는 거의 항상 "지난달 A에 이어", "다음 주 B 예정" 같은 서술이 있다. 키워드로는 도달할 수 없는 사건을 **기사가 직접 알려주는 경로**다.
>
> 동시에 가장 위험한 단계이기도 하다. 뉴스는 항상 이전·이후를 언급하므로 연쇄가 스스로 끊기지 않는다. 기간 제한과 깊이 상한이 안전장치다 ([타임라인 종료 정책](../requirements/timeline.md#수집-루프-종료-정책)).

### 2.7 P6 · 충분성 검토

**목적**: 모인 이벤트가 타임라인을 설명하기에 충분한지 판단한다. **재현율(recall) 담당.**

**출력**
- 충분 여부
- 부족한 지점 (있다면)
- 갱신된 기간 (필요하다면)

**지시 요점** — 아래 체크리스트로 판단한다

- 사건의 시작과 끝이 명확한가
- 날짜 간격에 설명되지 않는 공백이 있는가
- 수집된 기사가 언급하는 사건 중 다루지 못한 것이 있는가
- 기간을 넓히거나 좁혀야 하는가

> 체크리스트를 명시하는 이유: "충분한가"만 물으면 라운드마다 판단이 흔들려 종료 시점이 불안정해진다 ([PRD 공통 리스크](../REQUIREMENTS.md#7-공통-리스크)).

### 2.8 P7 · 가상 이벤트 생성

**목적**: 부족한 지점을 메울 검색 씨앗을 만든다.

**출력**: 추가 가상 이벤트 목록 (예상 시점, 예상 내용)

**지시 요점**
- P2와 같은 원칙. 사실로 단정하지 않는다
- 이미 확보된 이벤트와 겹치지 않는 지점을 겨냥한다

### 2.9 P8 · 타임라인 병합

**목적**: 선정된 기사와 대응 정보를 하나의 타임라인으로 정리한다.

**출력**
- 표시 제목
- 이슈 요약 (마크다운)
- 이벤트 목록 (날짜, 제목, 요약, 근거 기사 ID)

**지시 요점**
- 기사 ID는 **입력에 있는 값만** 사용한다
- 근거 기사가 없는 이벤트는 만들지 않는다
- **가상 이벤트를 결과에 포함하지 않는다.** 입력으로 주어진 실제 기사만 근거로 삼는다
- 이벤트는 시간순으로 정리한다
- 날짜와 근거 기사 집합이 같은 이벤트는 하나로 병합한다

### 2.10 P9 · 엔티티·관계 추출

**목적**: 기사 본문에서 인물·기관·장소·사건과 그 관계를 뽑는다.

**출력**
- 엔티티 목록 (표기, 유형)
- 관계 목록 (주체, 대상, 관계 유형)

**지시 요점**
- 기사에 등장하는 표기를 **그대로** 사용한다. 정식 명칭으로 바꾸지 않는다
- 기사에 서술된 관계만 추출한다. 일반 상식으로 연결하지 않는다

> 표기를 그대로 두는 것은 정규화를 하지 않기로 한 결정의 결과다. 대신 그래프를 기사별로 구성해 파편화를 피한다 ([지식 그래프 요구사항](../requirements/knowledge-graph.md)).

### 3.3 프롬프트 요점

**근거 사용**
- 이슈 문맥으로 답할 수 있는 일반적 질문은 바로 답한다
- **구체적 사실**(발언, 수치, 날짜, 인과관계)은 반드시 검색·조회 후 답한다
- 확신할 수 없으면 추측하지 않고 검색한다

**출처 구분** — CHAT-004

| 답변 내용 | 표기 |
|---|---|
| 검색·조회한 기사에서 확인된 내용 | 근거 기사 ID를 함께 제시 |
| 기사에 없는 배경 개념·용어 설명 | 기사에서 확인되지 않은 내용임을 명시 |
| 둘이 한 답변에 섞인 경우 | 문단 단위로 분리해 각각 표기 |
| 기사에도 없고 일반 지식으로도 확신할 수 없는 경우 | 답하지 않고 확인 불가를 알린다 |

**내보내기**
- 명시적으로 요청받은 경우에만 `export_briefing`을 호출한다
- 형식이 명시되지 않으면 되묻는다. 임의로 정하지 않는다
- 대상은 직전 답변이 아니라 **이슈 브리핑**이다

화면 표기 방식은 [`SCREENS.md`](../product/screens.md)를 원천으로 한다.

## 4. Embedding 및 Vector Search

### 4.1 임베딩 대상

기사 1건이 벡터 1개에 대응한다. 임베딩 텍스트는 `제목 + 요약 + 본문`을 결합해 구성한다.

> 청킹하지 않는다. 시드 규모가 작고, 근거 귀속이 기사 단위이므로 **기사와 벡터를 1:1로 유지**하는 편이 단순하다.

### 4.2 컬렉션 설계

| 항목 | 값 |
|---|---|
| 컬렉션명 | `articles` |
| dense named vector | `dense`, Cosine, 차원은 임베딩 모델 기준으로 착수 시 확인 |
| sparse named vector | `bm25`, Qdrant BM25, IDF modifier |
| BM25 텍스트 처리 | multilingual tokenizer, stemmer 없음, stopwords 없음 |
| payload | `article_id`, `service_date`, `title`, `category_middle` |

`title + summary + content` 결합 문자열은 dense와 BM25 vector 생성에 모두 쓰지만 payload에는
저장하지 않는다. dense 임베딩이 실패한 기사도 `bm25`만 적재해 키워드 검색 대상으로 남긴다.

payload에 `service_date`를 두는 이유는 **기간 필터를 검색 단계에서 적용**하기 위함이다
(NFR-05). 키워드와 의미 검색 모두 Qdrant query filter로 기간을 먼저 제한한 뒤 `top_k`를
적용한다.

### 4.3 키워드 검색

P3가 만든 키워드 묶음과 `OR`·`AND` 연산자를 `KeywordQuery`로 전달한다. Qdrant 어댑터는
각 term을 같은 기간 필터로 BM25 검색하고, OR은 기사 ID 합집합, AND는 교집합으로 결합한다.
같은 기사에 대한 term별 BM25 점수는 합산하며 집합 결합 뒤 최종 `top_k`를 적용한다.

BM25 ingest와 query는 같은 multilingual tokenizer 설정을 사용한다. 기본 영어 stemming과
stopword 제거는 한국어 기사에 적용하지 않는다.

### 4.4 결합 검색

RRF(Reciprocal Rank Fusion)로 순위를 결합한다.

```
score(d) = Σ  1 / (k + rank_i(d))
```

`k=60`, 각 검색 목록의 순위는 1부터 시작한다. RRF 점수가 같으면 `article_id` 오름차순으로
정렬한다. 같은 검색 목록에 기사 ID가 중복되면 첫 순위만 점수에 반영한다. `top_k`는 1 이상,
`k`는 0 이상만 허용한다. Qdrant의 내장 fusion을 쓰지 않고 `core.ranking`의 순수 함수로
계산한다.

관련 결정: [ADR-0003](../decisions/0003-search-strategies.md),
[ADR-0005](../decisions/0005-qdrant-dense-sparse-search.md)

## 5. 할루시네이션 방지 전략

이 제품의 핵심 문제가 신뢰성이므로([PRD 문제 정의](../REQUIREMENTS.md#2-문제-정의)) 방어를 여러 겹으로 둔다.

### 5.1 가상 이벤트 차단 — 이 파이프라인 고유의 위험

파이프라인이 **없는 사건을 상상해서 검색하는 구조**다. 상상한 이벤트가 결과물로 새어 나가면 완전한 허구가 사실처럼 제시된다.

| 계층 | 방어 |
|---|---|
| P8 프롬프트 | 입력으로 주어진 실제 기사만 근거로 삼도록 지시 |
| P8 입력 구성 | **가상 이벤트를 P8 입력에 넣지 않는다.** 선정된 실제 기사와 대응 정보만 전달 |
| 저장 전 검증 | 모든 이벤트에 근거 기사가 1건 이상인지 확인. 0건이면 제외 |
| DB 제약 | 외래키로 미실재 기사 참조를 거부 |

**두 번째 계층이 가장 확실하다.** 프롬프트로 "쓰지 마라"고 하는 것보다, 애초에 입력에 넣지 않는 편이 안전하다.

### 5.2 인용 대조

생성된 모든 `article_id`를 실제 기사 집합과 대조한다.

| 상황 | 처리 |
|---|---|
| 존재하지 않는 ID | 제거 |
| 근거가 0건이 된 이벤트 | 제외 |
| 중복 인용 | 병합 |

관련: AC-008

### 5.3 외래키 강제

이벤트-기사 연결 테이블에 외래키를 건다. **검증 로직에 버그가 있어도 DB가 미실재 기사 참조를 거부**한다 (NFR-09).

### 5.4 근거 노출

모든 이벤트에 대표 근거 기사를 즉시 표시하고 원문으로 이동할 수 있게 한다 (ART-001, ART-002).

### 5.5 대화 출처 구분

기사 근거와 일반 지식을 구분해 표기한다 (CHAT-004, §3.3).

### 5.6 그래프 출처 귀속

엔티티·관계는 출처 기사가 있어야만 저장한다. 모든 노드·간선이 어느 기사에서 왔는지 추적 가능하다 (NFR-16).

### 5.7 방어 계층 요약

```
프롬프트 지시      →  약함 (지시일 뿐)
     ↓
입력에서 배제      →  강함 (넣지 않으면 나올 수 없음)
     ↓
인용 대조          →  강함 (코드가 검증)
     ↓
외래키             →  가장 강함 (DB가 거부)
     ↓
근거 노출          →  사용자 검증 가능
```
