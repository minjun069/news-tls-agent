## 2. 문제 정의

### 2.1 제품 배경

뉴스는 사건 단위가 아니라 기사 단위로 유통된다. 하나의 사건이 수십에서 수백 건의 기사로 쪼개져 시간에 흩뿌려지고, 같은 사실이 여러 매체에서 반복 보도된다.

사용자가 사건의 전개를 파악하려면 포털 검색 결과를 날짜순으로 훑으며 중복을 스스로 걸러내야 한다. 포털은 최신순·정확도순 정렬만 제공할 뿐 "사건의 흐름"으로 묶어주지 않는다.

LLM에 물으면 요약은 얻을 수 있지만 근거 기사를 특정할 수 없어 사실 확인이 불가능하다. 학습 시점 이후의 사건은 아예 답하지 못한다.

news-tls-agent는 보유한 뉴스 아카이브를 근거로 사건을 시간순으로 재구성하고, 각 분기점마다 출처 기사를 귀속시켜 신뢰할 수 있는 형태로 제공하는 서비스다.

### 2.2 문제 정의

사용자가 하나의 이슈를 파악하는 데 드는 시간의 대부분은 **정보를 조직화하는 작업**에 쓰인다.

1. 흩어진 기사에서 사건의 순서를 스스로 재구성한다
2. 같은 사실을 반복 보도한 중복 기사를 직접 걸러낸다
3. 무엇이 중요한 분기점인지 판단한다
4. 필요한 세부 사실을 찾기 위해 기사를 다시 뒤진다

AI 요약은 이 시간을 줄여주는 것처럼 보이지만, **근거를 알 수 없으면 결국 확인 작업이 다시 발생**한다. 요약을 믿을 수 없으면 사용자는 원문을 다시 읽게 되고, 절감했다고 생각한 시간이 되돌아온다. 신뢰성이 없는 요약은 조직화 시간을 줄이지 못한다.

따라서 이 제품의 핵심 문제는 다음과 같다.

> **신뢰성이 확보된 상태로 정보를 조직화해, 사용자가 이슈를 파악하는 데 드는 시간을 크게 줄이는 것.**

근거 귀속은 목적이 아니라 **신뢰성을 확보하는 수단**이다. 사용자가 매번 원문을 확인해야 한다면 시간 절감에 실패한 것이다. 확인 경로는 열어두되, 확인하지 않아도 신뢰할 수 있어야 한다.

**검증 가설**: 각 분기점에 근거 기사가 귀속되고 그 근거를 바탕으로 대화할 수 있으면, 사용자는 원문을 직접 읽지 않고도 이슈를 신뢰 가능한 수준으로 파악할 수 있다.

## 3. 목표와 비목표

### 3.1 목표

**Product Goals**

- 흩어진 기사를 사건 단위 타임라인으로 조직화해 이슈 파악 시간을 줄인다.
- 모든 서술에 근거를 귀속시켜, 사용자가 원문 확인 없이도 내용을 신뢰할 수 있게 한다.
- 정리된 결과를 외부로 내보내 다른 작업에서 재사용할 수 있게 한다.

**User Goals**

- 관심 있는 이슈의 전개를 시간순 타임라인으로 한눈에 파악한다.
- 각 분기점의 대표 근거 기사를 즉시 확인하고, 필요하면 원문으로 바로 이동한다.
- **원문을 읽지 않고도** 기사를 근거로 한 대화를 통해 세부 내용을 습득한다.
- 기사에 없는 배경 개념·용어도 대화로 확인해 이슈를 이해한다.
- 정리된 브리핑을 PDF로 받거나 Notion에 저장해 다른 작업에서 활용한다.

**Project Goals**

- MCP 기반 데이터 접근 계층, MS-SQL 정규화 스키마, 벡터 DB 하이브리드 검색을 실제 동작하는 서비스로 구현한다.
- AI Agent 구현 및 모니터링 체계를 구축한다.
- 지식 그래프 구축 및 시각화를 구현한다.
- AI 개발 하네스(AGENTS.md, 권한 설정, 훅)를 구축해 반복 작업 비용을 줄인다.
- CI/CD 체계를 갖춰 품질 검증을 자동화한다.
- 각 설계 결정의 배경과 근거를 문서로 남겨 선택을 설명할 수 있는 상태를 만든다.

> 이 프로젝트는 상업 서비스가 아니므로 Business Goals 대신 **Project Goals**를 쓴다. 수익·성장 목표가 존재하지 않는다.

## 4. 사용자 시나리오

### 4.1 핵심 사용자

| 사용자       | 설명                            | 핵심 니즈               |
| --------- | ----------------------------- | ------------------- |
| 이슈 추적자    | 특정 사건의 전개 과정을 빠르게 파악하려는 사용자   | 사건 흐름을 시간순으로 한눈에    |
| 심화 질문자    | 요약에 없는 세부와 배경 개념을 확인하려는 사용자   | 근거를 갖춘 답변과 개념 설명    |
| 정리·활용 사용자 | 파악한 내용을 문서로 남겨 다른 작업에 쓰려는 사용자 | PDF 다운로드, Notion 저장 |

### 4.2 시나리오

#### 시나리오 1. 새 이슈 타임라인 생성

1. 사용자는 파악하고 싶은 이슈를 떠올리고 서비스에 접속한다.
2. 이슈 목록에 원하는 토픽이 없어 새 토픽을 입력한다.
3. 생성이 시작되고 현재 어떤 단계가 진행 중인지 확인한다.
4. 생성이 완료되면 시간순으로 정렬된 이벤트 목록을 본다.
5. 요약을 읽고 이슈의 전체 흐름을 파악한다.
6. 사용자는 타임라인에서 관심 있는 마일스톤을 선택하여 해당 이벤트의 대표 기사를 확인한다.
7. 사용자는 대표 기사의 제목·날짜·본문을 보고 이벤트 서술과 대조한다.
8. 더 확인하고 싶으면 나머지 근거 기사를 관련도 순으로 열어본다.
9. 원 매체에서 확인하려면 원문 URL로 이동한다.

#### 시나리오 2. 대화로 세부와 배경 습득

1. 사용자는 요약에 나오지 않은 세부 사실이 궁금하다.
2. 이슈 화면에서 에이전트에게 질문한다.
3. 에이전트가 기사를 검색하는 중임을 확인한다.
4. **원문을 직접 읽지 않고** 기사에 근거한 답변으로 내용을 파악한다.
5. 답변에 모르는 용어가 나와 그 개념이 무엇인지 이어서 묻는다.
6. 기사에 없는 배경 개념이라는 표시와 함께 설명을 받고 이슈를 이해한다.

#### 시나리오 3. 브리핑 활용

1. 사용자는 파악한 이슈를 기록으로 남기고 싶다.
2. 대화 중에 "이 내용을 PDF로 저장해줘"라고 말한다.
3. 에이전트가 의도를 파악해 내보내기를 수행하고 파일을 제공한다.
4. 또는 화면의 내보내기 메뉴에서 Notion 저장을 선택해 지정한 상위 페이지 아래에 페이지를 만든다.

## 6. 기능 상세 명세

> 각 기능의 **관련 AC · 예외**는 사용자에게 보이는 결과(AC)와 내부 처리 규칙(EX)을 함께 가리킨다.
> AC와 EX는 같은 상황의 밖과 안이므로, 구현자는 둘을 함께 봐야 한다.
>
> 구현 방식·최적화·파라미터는 여기에 쓰지 않는다. 기술 설계서(`TECH_DESIGN.md`)를 원천으로 한다.
> 이 절에는 **사용자가 보거나 겪는 것이 달라지는 사항**만 담는다.

### 6.1 타임라인 생성

- **입력**: 토픽 문자열

- **처리**

```
질의 의도 해석  ⇄  의도 되묻기        의도가 모호하면 되묻고 다시 해석
        │
        ▼
가상 타임라인 생성                    기간 설정 + 가상 이벤트 설정(시점, 내용)
        │
        ▼
   ┌─▶ 검색                          키워드 선정(OR/AND) · 문장 생성
   │     │
   │     ├── 결과 없음 ────────────────────────┐
   │     ▼ 결과 있음                            │
   │   핵심 이벤트 선정                          │
   │     │  타임라인에 정확하게 적합한 이벤트     │
   │     ├── 선정된 이벤트 없음 ────────────────┤
   │     ▼ 선정된 이벤트 있음                    │
   │   선후 이벤트 추출                          │
   │     │  핵심 이벤트 기사에 서술된 선후 사건   │
   │     ├── 추출된 선후 이벤트 없음 ───────────┤
   │     │                                      │
   └─────┴── 추출된 선후 이벤트 있음 (재검색)    │
                                                ▼
                                          진행 판정
                                            ├─ 충분성 검토 전이거나
                                            │  선정 기사 수가 달라짐 ─▶ 충분성 검토
                                            └─ 선정 기사 수 변화 없음 ─▶ 타임라인 생성
                                                │
                                                ▼
                                          충분성 검토
                                            │  선정된 이벤트들이 타임라인을
                                            │  충분하게 설명하는지 검토
                                            ├─ 부족 ─▶ 가상 이벤트 생성 ─▶ 검색
                                            └─ 충분 ─────────────────────┐
                                                                         ▼
                                                                   타임라인 생성
                                                                         │
                                                                         ▼
                                                                 인용 검증 · 저장
```

- **출력**: 진행 단계와 라운드 정보, 완료 시 생성된 이슈

- **제약사항**
  - **가상 타임라인과 가상 이벤트는 검색을 이끌기 위한 것이다. 최종 타임라인에 포함하지 않는다**
  - 가상 타임라인의 기간은 고정이 아니다. 충분성 검토 결과에 따라 갱신될 수 있다
  - 선후 이벤트 추출은 그 시점의 가상 타임라인 기간 안에서만 수행한다

- **관련 정책**: §7.2 수집 루프 종료
- **관련 AC · 예외**: AC-001, AC-002, AC-003, AC-008, AC-022, AC-023 · EX-01, EX-02, EX-03

> 첫 번째 제약이 이 파이프라인의 안전장치다. 없는 사건을 상상해 검색하는 구조이므로,
> 상상한 이벤트가 결과물로 새어 나가면 §2.2의 신뢰성 요건이 무너진다.

### 6.2 이슈 조회

- **입력**: (목록) 없음 / (상세) 이슈 식별자 / (기사) 기사 식별자

- **처리**
  - 목록: 저장된 이슈를 생성 시각 내림차순으로 조회
  - 상세: 이슈 조회 → 이벤트를 날짜 오름차순 정렬 → 이벤트별 근거 기사 연결 → 대표 기사 선정
  - 기사: 데이터 접근 계층을 통해 원문 조회

- **출력**
  - 목록: 토픽·제목·생성시각·이벤트 수
  - 상세: 요약, 이벤트 목록, 이벤트별 대표 기사와 근거 기사 목록
  - 기사: 제목·부제목·서비스 일자·본문·원문 URL

- **제약사항**
  - 기사 본문은 표시 상한까지만 반환한다. 전체 본문을 반환하지 않는다

- **관련 정책**: §7.1 대표 기사 선정
- **관련 AC · 예외**: AC-004, AC-005, AC-006, AC-007, AC-009, AC-010 · EX-04

### 6.3 이슈 질의

- **입력**: 이슈 식별자, 사용자 질문, 이전 대화 이력

- **처리**
  1. 이슈 문맥을 시스템 지시에 주입
  2. 에이전트 실행
  3. 필요 시 MCP 도구 호출 (기사 검색·조회, 내보내기)
  4. 출처를 구분해 응답 생성

- **출력**: 생성 중인 답변 텍스트, 도구 호출 진행 표시, 참조 기사 ID

- **제약사항**: 없음

- **관련 AC · 예외**: AC-011, AC-012, AC-013, AC-014, AC-015, AC-016 · EX-03, EX-05

> 컨텍스트 주입 범위와 대화 이력 유지 방식은 이번 범위에서 정하지 않는다 (§3.2).

### 6.4 브리핑 내보내기

- **입력**: 이슈 식별자, 형식(PDF / Notion), (Notion) 상위 페이지 식별자

- **처리**: 이슈 조회 → 브리핑 마크다운 구성 → 형식별 변환 → 파일 반환 또는 외부 저장

- **출력**: (PDF) 파일 / (Notion) 생성된 페이지 URL

- **제약사항**
  - 대화에서 호출될 때는 직전 답변이 아니라 **이슈 브리핑**을 대상으로 한다. 대상이 모호하면 되묻는다
  - Notion 연결 정보가 없으면 저장을 시도하지 않고 설정 안내를 반환한다

- **관련 AC · 예외**: AC-015, AC-016, AC-017, AC-018, AC-019 · EX-05

### 6.5 지식 그래프 생성

이슈에 등장하는 **엔티티(인물·기관·장소·사건 등)와 그 관계**를 그래프로 만든다.
이벤트–기사 인용 관계가 아니라 기사 내용에서 추출한 의미 관계다.

- **입력**: 이슈 식별자

- **처리**

```
대표 기사 목록 조회
     │
     ▼
관계 추출 여부 확인       기사별로 엔티티·관계가 저장돼 있는가
     │
     ├─ 미추출 기사 있음 ─▶ LLM으로 엔티티·관계 추출 ─▶ 기사 단위로 저장
     │                                                      │
     └──────────────────────────────────────────────────────┘
     │
     ▼
엔티티·관계 조회          대표 기사에 귀속된 엔티티·관계를 불러옴
     │
     ▼
그래프 구성               기사별로 그래프를 각각 구성
```

- **출력**: 기사별 그래프 목록. 각 그래프는 노드(엔티티), 간선(관계), 출처 기사 ID를 가진다

- **제약사항**
  - **그래프는 기사 단위로 구성한다.** 여러 기사를 하나의 통합 그래프로 합치지 않는다
  - 출처 기사가 없는 엔티티·관계는 저장하지 않는다
  - 엔티티 표기는 **표면형 그대로** 사용한다. 동일 인물의 다른 호칭을 병합하지 않는다
  - 이벤트가 1건 이하면 그래프를 제공하지 않는다

- **관련 AC · 예외**: AC-020, AC-021 · EX-03

> 기사별 구성을 택한 이유는 **엔티티 표기를 정규화하지 않기 때문**이다.
> 정규화 없이 여러 기사를 합치면 같은 인물이 여러 노드로 갈라져 판독이 어려워진다.

## 7. 정책

상태값 정의는 데이터 파이프라인 문서(`DATA.md`)를 원천으로 한다.
화면 표기 규칙은 화면설계서(`SCREENS.md`)를 원천으로 한다.

### 7.1 대표 기사 선정 정책

| 조건 | 선정 기준 |
|---|---|
| 근거 기사가 1건 | 해당 기사 |
| 근거 기사가 2건 이상 | 검색 관련도 점수가 가장 높은 기사 |
| 관련도 점수가 동일 | 서비스 일자가 이벤트 날짜에 가장 가까운 기사 |
| 위 조건으로도 동일 | 기사 ID가 작은 쪽 |

> 마지막 두 단계는 **표시를 결정론적으로 만들기 위한 것**이다. 같은 이슈를 두 번 열었을 때 다른 기사가 뜨면 사용자가 혼란을 겪는다.

### 7.2 수집 루프 종료 정책

§6.1의 루프는 아래 조건 중 **하나라도 만족하면 종료**하고 타임라인 생성으로 넘어간다.

| 조건 | 근거 |
|---|---|
| 충분성 검토 통과 | 정상 종료 |
| 충분성 검토를 거친 뒤 선정 기사 수가 달라지지 않음 | 수렴. 더 돌려도 같은 결과 |
| 선후 이벤트 연쇄가 깊이 상한에 도달 | 연쇄가 스스로 끊기지 않을 수 있음 |
| 최대 라운드 도달 | 비용 상한 |

> 충분성 검토만으로는 종료가 보장되지 않는다. LLM이 계속 부족하다고 판단하면 무한 루프가 된다.
> 특히 **선후 이벤트 추출 경로는 수렴 조건에 걸리지 않는다** — 기사 수가 계속 늘어나기 때문이다.
> 뉴스는 거의 항상 이전·이후 사건을 언급하므로 별도의 깊이 제한이 필요하다.

### 7.3 예외 케이스

**사용자가 관찰할 수 없는 내부 처리 규칙만** 여기에 둔다. 사용자에게 보이는 결과는 §5.2 AC가 정의한다.

| ID | 상황 | 기대 동작 |
|---|---|---|
| EX-01 | **최초 검색** 결과 0건 | 즉시 중단한다. 루프를 돌지 않는다 |
| EX-02 | 루프 도중 검색 결과 0건인데 누적 선정 기사도 0건 | 타임라인을 생성하지 않는다. 근거 0건인 이슈를 저장하지 않는다 |
| EX-03 | LLM 호출 실패 (타임아웃·빈 응답·안전필터 차단) | 1회 재시도. 재실패 시 저장하지 않는다 |
| EX-04 | 외부 API 호출 한도 초과 | 지수 백오프로 재시도. 최대 재시도 초과 시 실패 처리 |
| EX-05 | 저장 중 오류 발생 | **부분 저장 금지.** 이슈·이벤트·기사연결을 단일 트랜잭션으로 처리 |
| EX-06 | 데이터 접근 계층 연결 실패 | 기동 시점에 감지해 기록한다 |

> EX-02가 필요한 이유: 수렴 판정("선정 기사 수가 달라지지 않음")은 기사 수가 **0으로 그대로인 경우에도 성립**한다.
> 이 조항이 없으면 근거가 하나도 없는 상태로 타임라인 생성 단계에 진입한다.

## 8. 오픈 이슈

| 리스크 | 영향 | 대응 방안 |
|---|---|---|
| 선후 이벤트 연쇄가 끊기지 않음 | 루프가 길어지고 범위를 벗어남 | 가상 타임라인 기간으로 경계를 두고, 연쇄 깊이 상한을 적용 (§7.2) |
| 가상 이벤트가 최종 결과에 섞임 | §2.2의 신뢰성 요건이 무너짐 | §6.1 제약으로 금지. 저장 직전 인용 검증에서 재확인 |
| 충분성 판단이 라운드마다 일관되지 않음 | 종료 시점이 불안정 | 판단 체크리스트를 프롬프트에 명시(시작·끝 명확성, 날짜 공백, 미다룬 후속 사건) |
| 의도 되묻기가 반복되어 진행이 막힘 | 사용자가 이탈 | 되묻기 횟수에 상한을 두고, 이후에는 해석된 의도로 진행 |
| 일반 지식 답변이 기사 근거처럼 보일 위험 | §2.2의 신뢰성 요건이 무너짐 | CHAT-004 + 화면설계서의 출처 표기 규칙 |
| 지식 그래프 추출의 LLM 호출 비용 | 첫 조회 지연 | 기사 단위 저장으로 재사용. 같은 기사는 1회만 추출 |
| 엔티티 표기가 제각각이라 노드가 갈라짐 | 그래프 판독성 저하 | 기사별 구성으로 완화. 표기 정규화는 이번 범위 밖 |
| LLM의 도구 호출 동작이 에이전트 프레임워크와 맞지 않을 가능성 | 대화 기능 전체가 막힘 | 착수 직후 최소 예제로 선검증 |
| 시드 벡터 적재 시 임베딩 API 한도 초과 | **1회성 적재 작업 지연.** 런타임에는 쿼리 1건만 임베딩하므로 영향 없음 | 배치 크기 조절 + 재시도 |
| MS-SQL의 TCP/IP 프로토콜이 기본 비활성 | 드라이버 접속 실패 | 설치 체크리스트에 활성화 단계 포함 |
