# Codex 작업 방식과 피드백 루프

관련: [`AGENTS.md`](../../AGENTS.md) §1·§4·§5 · [`roadmap.md`](roadmap.md)

이 문서는 **어떻게 일하는가**의 단일 원천이다. 제품 범위는 PRD, 구현 설계는 아키텍처·AI·계약 문서가 정의한다.

## 1. 원칙

### 1.1 실제 상태와 Git 상태를 구분한다

Git은 파일의 추적 여부와 이력을 알려줄 뿐, 실제 파일·데이터·서비스의 존재와 정상 동작을 증명하지 않는다.

| 확인 대상 | 직접 확인할 증거 | Git이 답하는 것 |
|---|---|---|
| 파일 | 실제 경로, 크기, 내용 | 추적·변경 여부 |
| 원본 데이터 | 행 수, 필드, 표본 파싱, 전처리 결과 | 저장소 포함 여부 |
| MS-SQL | 카탈로그, 마이그레이션 이력, 실제 쿼리 | DDL 파일 이력 |
| Qdrant·컨테이너 | 실행 상태, 헬스, 컬렉션 | compose 변경 이력 |
| API·MCP | 실제 요청·응답·Inspector | 구현 파일 변경 이력 |

직접 확인하지 않은 상태는 “없음”이나 “완료”가 아니라 **미확인**이다. 특히 `data/raw/`처럼 Git에서 제외된 경로는 작업 시작 시 실제 디렉터리를 먼저 본다.

### 1.2 틀렸다는 걸 알기까지의 시간을 줄인다

개발 속도는 작성 속도보다 잘못된 전제를 발견하는 속도에 좌우된다. 자동 루프는 한 명령으로 실행되고, 판정이 통과/실패로 명확하며, 실패 메시지가 원인을 알려야 한다.

### 1.3 대상이 생긴 뒤 루프를 만든다

인터페이스가 없는 모의 LLM, 화면이 없는 시각 회귀, 비교 대상이 없는 검색 평가는 먼저 만들지 않는다. 실제 대상과 같은 스프린트에서 만든다.

## 2. 작업 시작 흐름

1. `AGENTS.md` §4에서 작업 종류를 찾는다.
2. 표의 문서를 왼쪽부터 읽는다.
3. 변경 후보 경로가 있으면 `python3 .harness/route_docs.py <경로...>`로 추가 계약 문서를 확인한다.
4. 요구사항 ID/Project Goal, 지금 필요한 이유, 산출물 위치를 확인한다.
5. 파일·데이터·서비스의 실제 상태를 직접 확인하고 작업한다.

Codex의 PreToolUse 훅은 패치 대상 경로를 보고 관련 계약 문서를 다시 알려준다. 이 훅은 맥락을 보강하는 가드레일이며 완전한 강제 경계가 아니다. 최종 강제는 `make check`와 CI의 문서 동기화 검사다.

## 3. 상황별 피드백 루프

| ID | 상황 | 수단 | 도입 시점 |
|---|---|---|---|
| L1 | Python 편집 직후 | Codex PostToolUse → ruff·import-linter | S1 |
| L2 | 커밋 전 | `make check` → lint·arch·unit·docs | S1 |
| L3 | PR | GitHub Actions | S1, 통합은 S9 확장 |
| L4 | 상위 지침 변경 | `make agent-budget` 측정; 목표 기준은 사용자 결정 대기 | S1 |
| L5 | 계약 코드 변경 | `.harness/doc-routes.json` 기반 동반 변경 검사 | S1 |
| L6 | 검색 방식 변경 | 같은 입력 집합의 3종 결과 비교 | S3 |
| L7 | MCP 툴 작성 | Inspector + payload 단위 테스트 | S4 |
| L8 | 파이프라인 변경 | 인터페이스 확정 후 모의 LLM 단위 테스트 | S5 |
| L9 | 화면 변경 | `web-check` + 사람의 화면 기준 확인 | S7 |
| L10 | 계약 코드 편집 시도 | Codex PreToolUse 문서 라우팅 알림 | S1 |
| L11 | 스키마 변경 | 마이그레이션 재실행·카탈로그 확인 | S2 |

L5와 L10은 짝이다. L10이 쓰기 전에 읽을 문서를 알려주고, L5가 쓴 뒤 계약 문서가 같이 바뀌었는지 검사한다.

### 파이프라인 검증

모의 LLM 픽스처는 파이프라인 입력·출력 인터페이스가 정해지는 S5에서 만든다. 다음 구조를 초 단위로 확인한다.

- 종료 조건 네 가지
- 존재하지 않는 기사 ID 저장 차단
- 가상 이벤트의 최종 결과 유출 차단
- 라운드별 호출 수 상한

LLM 문장 자체의 골든 파일 대조는 사용하지 않는다. 비결정적 문장 대신 스키마·인용·상태 전이를 검증한다.

## 4. 제안 규칙

다음 질문을 통과하지 못하면 제안하지 않는다.

1. 어느 요구사항 ID 또는 Project Goal에 대응하는가?
2. 지금 하지 않으면 무엇이 막히는가?
3. 산출물이 어느 파일·테스트·실행 결과에 남는가?
4. MCP·MS-SQL·Qdrant 학습 목표와 계층 경계를 지키는가?
5. 새 설계 결정이면 ADR이 필요한가?

피해야 할 패턴:

- MS-SQL 경험이 목표인데 SQLite로 먼저 만든 뒤 교체
- 파이프라인 인터페이스가 없는데 모의 LLM부터 작성
- 비결정적 LLM 문장을 골든 파일로 비교
- PRD에 구현 파라미터를 넣거나 관측 요구를 제약으로 분류
- Git에서 안 보인다는 이유로 실제 파일이 없다고 판단

사용자가 “대답만”, “왜 필요한가”, “지금 필요한 논의인가”라고 물으면 편집을 멈추고 질문에 먼저 답한다.
