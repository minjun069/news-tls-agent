# S3 벡터 계층 실행계획

관련 요구사항: [NFR-04·NFR-05](../architecture/overview.md#32-검색)

검색 원천: [AI 명세 §4](../ai/specification.md#4-embedding-및-vector-search) · [ADR-0003](../decisions/0003-search-strategies.md)

상위 일정: [개발 로드맵 S3](roadmap.md#s3--벡터-계층)

이 문서는 S3의 **작업 순서, S2와의 병렬 경계, 작업 단위별 산출물, 모델 배정,
검증 게이트**를 관리한다. 검색 방식과 외부 동작은 위 요구사항·AI 명세·ADR이 단일 원천이며,
이 문서에서 다시 정의하지 않는다.

## 1. 목표와 현재 전제

S3의 목표는 BM25 키워드 검색, Qdrant 의미 검색, RRF(Reciprocal Rank Fusion) 결합 검색을
각각 호출할 수 있게 만들고, 기간 필터를 각 검색 단계에서 `top_k`보다 먼저 적용하는 것이다.

계획 작성 시점의 전제는 다음과 같다.

- S2와 S3 브랜치는 `2d9c54d`에서 분기했다.
- S2의 실제 원본 필드 매핑과 최종 `data/seed/<topic>.articles.jsonl` 생성은 아직 완료되지 않았다.
- `backend/infra/qdrant.py`, `backend/infra/embedding.py`, `backend/app/search.py`,
  `backend/scripts/03_build_vectors.py`는 아직 없다.
- 따라서 S2 진행 중에는 순수 계산·검색 계약·모의 어댑터까지만 구현하고, 실제 기사 임베딩과
  저장소 통합은 S2 산출물 이후에 수행한다.

## 2. 전체 의존 순서

```text
S2 진행 중
  S3-P1 검색 계약·BM25 위치 결정
        ├─ S3-P2 RRF 순수 함수와 단위 테스트
        └─ S3-P3 Qdrant·임베딩 어댑터와 모의 테스트

S2 완료
  S3-A1 S2 산출물 병합·감사
        ├─ S3-A2 BM25 실제 구현
        └─ S3-A3 03_build_vectors 구현·실행
                  ↓
        S3-A4 app/search.py 3종 검색 조립
                  ↓
        S3-A5 실데이터 비교·통합 검증
                  ↓
        S3-A6 문서·로드맵 종료 정리
```

S3-P1은 나머지 병렬 작업의 입력 계약이므로 먼저 끝낸다. P1 커밋 이후 P2와 P3는 서로 다른
파일을 중심으로 작업할 수 있다. S2 완료 뒤에는 A1로 실제 산출물을 확인한 다음 A2와 A3를
병렬 수행하고, 두 결과가 모두 준비된 뒤 A4에서 조립한다.

## 3. S2와 병렬로 수행할 작업

### S3-P1 · 검색 계약과 BM25 구현 위치 결정

| 항목 | 내용 |
|---|---|
| 관련 | NFR-04, NFR-05, ADR-0003 |
| 산출물 | `backend/core/models.py`, `backend/core/ports.py`, 관련 기술 문서와 기계 검사 |
| 권장 모델 | `gpt-5.6-sol` |
| 추론 수준 | `high` |

다음 항목을 코드와 문서에서 하나의 계약으로 확정한다.

- 검색 방식 `keyword`, `semantic`, `hybrid`
- 질의, `top_k`, `date_from`, `date_to`의 타입과 검증
- 검색 결과의 `article_id`, 점수, 검색 방식 표현
- 임베딩 공급자, 키워드 검색기, 벡터 저장소 포트
- Qdrant 결과의 기사 ID를 `Repository.get_articles()`로 복원하는 경계
- 기간 필터를 검색기 내부에서 `top_k`보다 먼저 적용한다는 규칙
- RRF의 기본 `k`, 순위 시작값, 동률 처리와 결정론 규칙

BM25 알고리즘은 `app/search.py`에 두지 않는다. `app`은 포트를 조립하고 실제 구현은
`infra` 어댑터가 담당한다. 우선 후보는 `infra/bm25.py`이며, 실제 백엔드는 아래 기준으로
비교한 뒤 기술 문서 또는 새 ADR에 기록한다.

- 일반 전문 검색 점수가 아니라 실제 BM25를 제공하는가
- 한국어 토큰화 방식이 명시되는가
- OR·AND 질의와 기간 선필터를 지원하는가
- S2 시드로 인덱스를 재구축할 수 있는가
- SQL이 필요할 경우 `infra/repository.py` 밖에 SQL을 작성하지 않는가

완료 조건은 P2와 P3가 SDK 타입이나 임시 타입을 새로 만들지 않고 이 계약만으로 구현을
시작할 수 있는 상태다.

### S3-P2 · RRF 순수 함수와 단위 테스트

| 항목 | 내용 |
|---|---|
| 관련 | NFR-04, ADR-0003 |
| 산출물 | `backend/core/ranking.py`, `backend/tests/unit/test_ranking.py` |
| 권장 모델 | `gpt-5.6-terra` |
| 추론 수준 | `medium` |

외부 저장소나 SDK 없이 순위 목록만 입력받아 RRF 점수와 정렬 결과를 반환한다. 다음 사례를
단위 테스트로 고정한다.

- 두 검색 목록에 모두 있는 기사와 한쪽에만 있는 기사
- 빈 목록과 단일 검색 목록
- 같은 검색 목록 안의 중복 기사 ID
- 같은 RRF 점수의 결정론적 순서
- `top_k` 절단과 입력 불변성

ADR-0003에서 제외한 검색기별 가중치와 `k` 튜닝은 추가하지 않는다.

### S3-P3 · Qdrant·임베딩 어댑터와 모의 테스트

| 항목 | 내용 |
|---|---|
| 관련 | NFR-04, NFR-05 |
| 산출물 | `backend/infra/qdrant.py`, `backend/infra/embedding.py`, 단위 테스트, 의존성·설정 |
| 권장 모델 | `gpt-5.6-terra` |
| 추론 수준 | `high` |

실제 API와 컨테이너를 호출하지 않고 주입한 가짜 클라이언트로 다음 동작을 검증한다.

- `articles` 컬렉션, Cosine 거리, 주입된 벡터 차원
- `article_id`, `service_date`, `title`, `category_middle` payload
- 같은 기사 ID 재적재의 멱등성
- Qdrant 기간 필터가 검색 요청에 포함되고 그 뒤 `top_k`가 적용되는지
- 문서 배치 임베딩과 단일 검색 질의 임베딩의 구분
- 자격증명·모델명의 환경변수 주입
- SDK 예외를 삼키지 않고 호출자가 재시도 여부를 판단할 수 있는 오류 경계

실제 임베딩 모델 사용 가능 여부와 벡터 차원은 S3-A3의 첫 실호출에서 확인한다. 확인 전에는
차원을 하드코딩하지 않는다.

### 병렬 기간의 명시적 제외 범위

아래 항목은 S2 산출물을 입력으로 확인하기 전에는 구현하거나 완료 처리하지 않는다.

- `backend/scripts/03_build_vectors.py` 구현과 실제 실행
- 실제 임베딩 API 호출과 실제 Qdrant 포인트 적재
- BM25 알고리즘과 한국어 토큰화 구현
- `backend/app/search.py`의 세 검색 방식 조립
- 실데이터 기간 필터 및 세 방식 결과 비교
- 로드맵의 S3 완료 체크

## 4. S2 완료 이후 수행할 작업

### S3-A1 · S2 산출물 병합과 감사

| 항목 | 내용 |
|---|---|
| 입력 | S2 완료 커밋, `data/seed/<topic>.articles.jsonl`, MS-SQL `articles` |
| 권장 모델 | `gpt-5.6-terra` |
| 추론 수준 | `medium` |

S2 완료 커밋을 S3 브랜치에 병합한 뒤 파일 존재를 Git 상태로 추론하지 않고 직접 확인한다.
각 시드 파일의 경로·크기·행 수·JSON 파싱·필드 스키마와 표본을 검사하고, MS-SQL은 카탈로그와
쿼리로 실제 기사 수를 확인한다. 불일치가 있으면 벡터 적재로 진행하지 않고 S2 계약과 산출물 중
어느 쪽이 다른지 먼저 해결한다.

### S3-A2 · BM25 실제 구현

| 항목 | 내용 |
|---|---|
| 입력 | P1의 위치 결정, A1에서 확인한 기사 집합 |
| 권장 모델 | `gpt-5.6-sol` |
| 추론 수준 | `high` |

선택한 `infra` 어댑터에 BM25, 한국어 토큰화, OR·AND 조합, 기간 선필터를 구현한다. 같은
입력과 인덱스에서 결과가 결정론적이어야 하며, 검색 후 날짜를 제거하는 방식은 허용하지 않는다.

### S3-A3 · 벡터 빌드 구현과 실제 실행

| 항목 | 내용 |
|---|---|
| 산출물 | `backend/scripts/03_build_vectors.py`, 실제 Qdrant `articles` 컬렉션 |
| 권장 모델 | `gpt-5.6-terra` |
| 추론 수준 | `high` |

시드 기사에서 `제목 + 요약 + 본문`을 결합하고 배치 임베딩, 지수 백오프 재시도, 컬렉션 생성,
포인트 upsert를 수행한다. 첫 실호출로 임베딩 모델과 벡터 차원을 확인해 설정·AI 명세를 같은
변경에서 갱신한다. 재실행 전후 포인트 수와 ID 집합을 비교해 멱등성을 검증한다.

### S3-A4 · 세 검색 방식 유스케이스 조립

| 항목 | 내용 |
|---|---|
| 산출물 | `backend/app/search.py`, 모의 포트 단위 테스트 |
| 권장 모델 | `gpt-5.6-sol` |
| 추론 수준 | `high` |

`app/search.py`는 `core.ports`만 주입받아 keyword·semantic·hybrid를 선택한다. hybrid는 P2의
RRF를 사용한다. 검색기가 반환한 ID는 Repository에서 원문 메타데이터로 복원하고, MS-SQL에
없는 ID는 결과에서 제외한다. `app`은 `infra`나 SDK를 직접 import하지 않는다.

### S3-A5 · 실데이터 통합 비교

| 항목 | 내용 |
|---|---|
| 권장 모델 | `gpt-5.6-sol` |
| 추론 수준 | 기본 `high`, 품질 원인 분석이 필요할 때만 `xhigh` |

같은 질의·기간·`top_k`로 세 방식을 각각 실행하고 다음을 기록한다.

- 각 방식이 독립 호출되고 결과가 실제로 다른지
- 정확 일치 질의에서 BM25가 고유명사·날짜를 찾는지
- 표현이 다른 개념 질의에서 의미 검색이 후보를 보완하는지
- hybrid가 두 순위를 RRF로 결합하는지
- 기간 밖 기사가 두 검색기에서 모두 후보가 되기 전에 제외되는지
- Qdrant 포인트 수, 벡터 설정, payload 형식, MS-SQL 기사 ID와의 대응

`make check`와 Qdrant·MS-SQL이 필요한 관련 통합 검사를 실행한다. 비교 결과가 기대와 다를
때만 `xhigh`로 토큰화·질의·필터·RRF 입력을 추적하며, 높은 추론 수준을 기본값으로 쓰지 않는다.

### S3-A6 · 종료 정리

| 항목 | 내용 |
|---|---|
| 권장 모델 | `gpt-5.6-luna` |
| 추론 수준 | `medium` |

변경 파일을 직접 다시 읽고 로드맵의 S3 체크리스트와 완료 기준을 검증 결과에 맞게 갱신한다.
종료 보고에는 문제, 미검증, 사용자 작업, 검증 결과를 각각 적고 없으면 `없음`이라고 쓴다.

## 5. 모델 배정 원칙

이 문서의 모델은 제품 런타임 LLM이나 임베딩 모델이 아니라 **Codex 구현 작업에 사용할 모델**을
뜻한다.

- `gpt-5.6-sol`: 계층 계약, BM25 위치, 여러 저장소를 가로지르는 조립처럼 잘못된 결정의
  수정 비용이 큰 작업
- `gpt-5.6-terra`: 입력·출력과 완료 조건이 정해진 순수 함수, 어댑터, 스크립트 구현
- `gpt-5.6-luna`: 검증 결과 정리와 체크리스트 갱신처럼 판단 범위가 좁은 반복 작업
- `medium`: 범위가 고정된 구현의 기본값
- `high`: 계약·외부 SDK·복수 저장소 경계를 함께 다루는 작업
- `xhigh`: 대표 실데이터에서 품질 문제가 재현되어 원인 분석이 필요할 때만 사용

`max`는 S3 기본 배정에서 제외한다. `high` 또는 `xhigh`와 동일한 대표 작업을 비교해 실질적인
품질 향상이 확인된 경우에만 별도로 사용한다. 모델 역할과 추론 수준의 기준은
[OpenAI 공식 모델 가이드](https://developers.openai.com/api/docs/guides/latest-model)를 따른다.

## 6. 작업 단위 공통 게이트

각 작업은 다음 순서로 종료한다.

1. 변경 파일을 직접 다시 읽는다.
2. `python3 .harness/route_docs.py <변경 경로...>`가 안내한 계약 문서를 대조한다.
3. 계약이 바뀌었으면 같은 커밋에서 문서와 기계 검사를 갱신한다.
4. `make check`를 실행한다.
5. 저장소·외부 API가 필요한 작업은 관련 통합 검사와 실제 상태 확인을 추가한다.
6. 다른 작업 단위의 관련 없는 변경을 커밋에 포함하지 않는다.
