## 배경

사용자가 대화 중에 "이 내용을 PDF로 저장해줘"라고 말하면 내보내기가 실행되어야 한다(CHAT-006). 이 의도를 어디서 판단할 것인가.

참고 사례가 있다. 이전 프로젝트는 LLM 호출 **앞단에 정규식 라우터**를 뒀다. 저장 동작 패턴, 형식 패턴, 생성 요청 패턴 등 5개 정규식으로 의도를 분류하고, 매치되면 LLM을 거치지 않고 바로 내보내기를 실행했다. 한국어 연결어미("해서 / 하고 / 한 뒤 / 다음에")를 정규식으로 벗겨내는 코드까지 있었다.

여기서 두 가지 문제가 관찰됐다.

1. **판단이 두 곳에서 일어났다.** 시스템 프롬프트는 "사용자가 명시적으로 요청한 경우에만 내보내기 도구를 사용하라"고 지시하는데, 정작 명시적 요청은 정규식이 먼저 가로채서 LLM에 도달하지 않았다. 같은 판단을 서로 다른 방식으로 두 번 한 셈이다.
2. **한국어 표현을 정규식으로 감당하려 했다.** 조사와 어순이 자유로워 패턴이 계속 늘어났고, 늘어난 패턴이 서로 간섭했다.

## 선택지

1. **정규식 라우터 유지** — LLM 호출을 아낄 수 있고 동작이 결정론적이다
2. **LLM으로 의도를 먼저 분류한 뒤 분기** — 분류 전용 호출이 한 번 더 든다
3. **도구 호출로 처리** — 내보내기를 도구로 노출하고, 부를지 말지는 에이전트가 판단한다

## 결정

3안을 채택한다. 내보내기는 **MCP 도구**로 노출하고, 호출 여부와 인자는 에이전트가 판단한다.
정규식이나 키워드 매칭으로 LLM 앞단에서 의도를 분류하지 않는다.

형식이 명시되지 않은 요청은 임의로 정하지 않고 되묻는다(AC-016). 되묻는 판단도 에이전트가 한다.

## 결과

- 판단 지점이 하나로 모인다. 프롬프트와 코드가 어긋날 여지가 사라진다.
- 한국어 표현 변형을 패턴으로 감당할 필요가 없어진다. 어순이 바뀌거나 완곡하게 말해도 동작한다.
- 화면 메뉴와 대화 두 진입점이 **같은 내보내기 구현**을 호출하게 된다. 경로별로 분기 로직이 갈라지지 않는다.
- **결정론이 약해진다.** 같은 문장에 대해 항상 같은 도구 호출이 일어난다고 보장할 수 없다. 이 위험은 AC-015·AC-016으로 검증한다.
- **LLM 호출이 필요해진다.** 정규식이라면 0회로 끝났을 요청도 에이전트를 거친다. 대화 흐름 안에서 처리되므로 추가 호출은 아니지만, 판단 실패 시 사용자가 다시 말해야 한다.
