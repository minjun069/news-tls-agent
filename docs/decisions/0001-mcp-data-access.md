## 배경

에이전트가 기사를 검색·조회하려면 데이터 접근 수단이 필요하다. 가장 단순한 방법은 파이썬 함수를 도구로 만들어 에이전트에 직접 주입하는 것이다.

이전 프로젝트가 그 방식이었고 다음 문제가 있었다.

- 도구 생성 시점에 이슈에 속한 기사 전체를 메모리로 읽고 검색 인덱스를 만들어야 했다. 이슈가 바뀔 때마다 전체가 재구축됐다.
- 인덱스가 웹 프로세스 안에 있어 재시작하면 사라지고, 워커를 늘리면 워커마다 중복 생성됐다.
- 데이터 접근이 여러 지점에서 일어나 **누가 무엇을 조회했는지 기록할 단일 지점이 없었다.**
- 같은 이름의 검색 함수가 두 곳에 서로 다른 구현으로 존재하게 됐다.

## 선택지

1. **파이썬 함수를 에이전트에 직접 주입** — 가장 단순하고 빠르다. 프로세스 경계가 없어 지연이 없다.
2. **내부 REST API로 분리** — 프로세스는 분리되지만 도구 정의를 클라이언트마다 다시 작성해야 한다.
3. **MCP 서버로 분리** — 도구 정의가 프로토콜 계약이 되어 클라이언트가 재사용한다.

## 결정

3안을 채택한다. 데이터 접근을 MCP 서버로 분리하고, API 서버가 MCP 클라이언트로 접속한다.
에이전트에 파이썬 함수를 직접 주입하지 않는다.

MCP 서버는 **LLM을 호출하지 않는다.** 도구를 언제 부를지 판단하는 것은 에이전트의 몫이고, 에이전트는 API 서버에 있다.

## 결과

- 검색 인덱스의 수명이 에이전트 수명에서 분리된다. 이슈 전환 시 재구축 문제가 사라진다.
- 데이터 접근이 단일 관문을 지나므로 **감사 로그를 한 곳에서 건다** (NFR-06).
- 같은 서버를 MCP Inspector와 API 서버 양쪽에 붙일 수 있다. 클라이언트가 늘어도 접근 계층을 재구현하지 않는다 (NFR-12).
- 인증·권한을 넣을 자리가 생긴다. 이번 범위에서 구현하지는 않지만 구조적으로 가능해진다.
- **프로세스 경계와 직렬화로 지연이 늘어난다.** 단일 클라이언트만 놓고 보면 1안이 빠르다. 이 비용은 위 이득과 학습 목표를 위해 감수한다.
- 장애 시 우회 경로를 두지 않기로 한다. MCP 서버에 연결할 수 없으면 오류를 반환하며, 저장소에 직접 접근하지 않는다 (EX-06). 우회를 한 번 허용하면 그 경로가 영구화되기 때문이다.
