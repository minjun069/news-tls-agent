## 배경

S9에서 API 서버와 MCP 서버를 각각 컨테이너 이미지로 게시하고, 전체 컨테이너 모드를 한
명령으로 기동해야 한다. 현재 MCP 계약은 stdio 전송이며 API의 `MCPToolClient`가 요청마다
`python -m mcp_server.server` 자식 프로세스를 시작한다. stdio는 컨테이너 네트워크 주소로
접속하는 전송이 아니므로 MCP를 별도 컨테이너에 둔 뒤 API가 HTTP처럼 호출할 수 없다.

이미지 경계를 정하면서 다음 조건을 함께 지켜야 한다.

- API의 데이터 조회는 계속 MCP 프로세스를 통과해야 한다.
- MCP 전송을 바꾸거나 네트워크용 두 번째 계약을 추가하지 않는다.
- API와 독립적으로 MCP 이미지를 실행해 다른 stdio 클라이언트가 사용할 수 있어야 한다.
- MS-SQL 마이그레이션이 앱보다 먼저 끝나야 한다.

## 선택지

1. **MCP를 HTTP 전송으로 바꿔 별도 컨테이너에 둔다** — 컨테이너 경계는 명확하지만 채택한
   stdio 계약과 MCP 클라이언트를 함께 바꿔야 한다.
2. **API 이미지에만 MCP 코드를 포함한다** — 현재 동작은 유지하지만 독립 MCP 이미지 게시라는
   S9 산출물이 없다.
3. **공통 백엔드 런타임에서 API·MCP·마이그레이션 대상을 나눈다** — API 대상은 MCP 모듈을
   포함해 자식 프로세스로 실행하고, MCP 대상은 같은 모듈을 stdio 진입점으로 노출한다.

## 결정

3안을 채택한다.

- `backend/Dockerfile`의 공통 `runtime`에 백엔드 코드, ODBC Driver 18, 한글 TTF를 넣는다.
- `api` 대상은 Uvicorn을 실행한다. API가 조회·대화·내보내기를 처리할 때 같은 이미지 안의
  `mcp_server.server`를 별도 자식 프로세스로 시작하므로 프로세스·직렬화·감사 경계가 유지된다.
- `mcp` 대상은 `python -m mcp_server.server`를 기본 명령으로 노출한다. 독립 클라이언트는
  표준 입력을 연결해 이 이미지를 사용할 수 있다.
- `migrate` 대상은 마이그레이션만 실행하고 종료한다. Compose의 `api`와 `mcp`는 이 서비스가
  성공한 뒤 시작한다.
- 전체 Compose의 독립 `mcp` 서비스는 이미지 기동과 외부 stdio 연결을 위한 인스턴스다.
  API는 이 컨테이너로 네트워크 우회하지 않고 자기 자식 MCP 프로세스를 사용한다.

태그 `v*`를 push하면 GitHub Actions가 같은 Dockerfile의 `api`와 `mcp` 대상을 각각
`ghcr.io/<owner>/<repository>-api:<tag>`,
`ghcr.io/<owner>/<repository>-mcp-server:<tag>`로 게시한다. 실제 서버 배포는 범위 밖이다.

## 결과

- API와 독립 MCP 이미지가 같은 코드·의존성에서 만들어져 도구 계약이 갈라지지 않는다.
- stdio 계약을 유지하므로 ADR-0001·ADR-0006의 장애 시 직접 저장소 우회 금지가 그대로 적용된다.
- API 컨테이너 안에는 Uvicorn과 요청별 MCP 자식 프로세스가 함께 존재한다. 컨테이너 하나가
  프로세스 하나라는 단순성보다 기존 프로토콜 경계를 우선한 비용이다.
- 전체 Compose에서는 독립 MCP 인스턴스와 API의 자식 MCP 인스턴스가 동시에 존재할 수 있다.
  두 인스턴스는 상태를 보유하지 않고 같은 MS-SQL·Qdrant를 사용하며 감사 로그 볼륨을 공유한다.
