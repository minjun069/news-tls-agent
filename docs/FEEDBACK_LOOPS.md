# 검증 루프와 제안 규칙 — news-tls-agent

관련: [`AGENTS.md`](../AGENTS.md) §8 · [`ROADMAP.md`](ROADMAP.md)

> 이 문서가 **작업 방식의 단일 원천**이다. 무엇을 만드는가는 PRD, 어떻게 만드는가는 기술 설계서, **어떻게 일하는가는 여기**다.

---

## 1. 원칙

### 1.1 틀렸다는 걸 알기까지의 시간

개발 속도를 결정하는 것은 코드를 쓰는 속도가 아니라 **틀렸다는 걸 아는 데 걸리는 시간**이다. 그 시간이 길수록 잘못된 전제 위에 쌓은 작업이 늘어난다.

### 1.2 AI가 스스로 검증할 수 있어야 한다

사람이 확인해줘야 하는 루프는 사람 속도로 느려진다. AI Native의 지렛대는 AI에게 코드를 쓰게 하는 것이 아니라, **AI가 자기 결과를 스스로 확인할 수 있는 환경**을 만드는 데 있다.

그래서 각 루프는 다음을 만족해야 한다.

- 명령 한 줄로 실행된다
- 판정이 기계적이다 (통과 / 실패)
- 실패 시 무엇이 틀렸는지 메시지에 있다

### 1.3 루프는 대상이 생길 때 만든다

검사할 코드가 없는데 검사 스크립트를 먼저 만들지 않는다. 대상 없는 검증 도구는 동작하지 않고, 나중에 실제 코드와 어긋난 채 발견된다.

L6·L9만 사람 판단이 필요하다. 나머지는 전부 기계 판정이다.

L5와 L10은 짝이다. L10이 **쓰기 전에** 계약을 읽히고, L5가 **쓴 뒤에** 계약이 갱신됐는지 본다.
L5 없이 L10만 두면 낡은 문서를 강제로 읽히게 되어 오히려 해롭다 — 라우팅은 문서 품질의 증폭기다.

### 2.1 이 프로젝트 고유의 루프

L5·L7·L8은 일반 웹 프로젝트에 없다. 셋 다 **LLM이나 외부 계약이 개입해 눈으로는 확인이 안 되는** 지점이다.

**L8이 가장 중요하다.** LLM 호출이 9종이고 수집 루프가 반복되므로, 실제 LLM으로 확인하면 매번 비용과 시간이 든다. 모의 LLM으로 아래를 초 단위에 잡는다.

- 종료 조건 4가지가 각각 동작하는가 (PRD §7.2)
- 허구 `article_id`가 저장되지 않는가 (AC-008)
- 가상 이벤트가 최종 결과에 섞이지 않는가 (AI_SPEC §5.1)
- 라운드당 호출 수가 예상 범위인가

> 모의 LLM 픽스처는 **파이프라인 인터페이스가 정해진 뒤**에만 만들 수 있다. 무엇을 주고 무엇을 받는지 모르면 흉내 낼 수 없다. S5에서 파이프라인과 함께 만든다.

### 2.2 하지 않기로 한 것

**LLM 출력의 골든 파일 테스트.** 같은 입력에 같은 출력이 나오지 않아 성립하지 않는다. 자동화 가능한 것은 구조 검증뿐이고, 그건 이미 Pydantic 검증과 인용 대조가 한다.

## 3. 제안 규칙

### 3.1 제안 전 확인

`AGENTS.md §8`의 5개 질문을 통과하지 못하면 제안하지 않는다. 그중 **3번이 가장 자주 걸린다.**

> **산출물이 어디에 기록되는가?** 기록할 곳이 없으면 시기상조다.

기록될 곳이 없는 논의는 다음 세션에 사라진다. 사라진다는 것은 **지금 할 필요가 없다는 뜻**이다.

### 3.2 걸러내야 할 패턴

이전 계획 단계에서 실제로 발생해 되돌린 것들이다.

| 패턴 | 사례 | 무엇이 잘못됐나 |
|---|---|---|
| 일반론을 검증 없이 적용 | "골든 케이스를 두자" | LLM 비결정성을 대조하지 않음 |
| 학습 목표와 반대 방향 | "SQLite로 먼저 만들고 MS-SQL로 교체" | MS-SQL 경험이 목표 자체인데 미룸 |
| 대상 없는 검증 도구 | "모의 LLM 픽스처를 먼저" | 파이프라인이 없는데 흉내 낼 수 없음 |
| 문서 경계 초과 | PRD에 구현 방식·파라미터 | PRD는 사용자가 겪는 것만 |
| 분류 오류 | "계측해 기록한다"를 제약사항에 | 제약은 금지·한계다. 이건 관측 요구 |
| 앞뒤 모순 | "손으로 해봐야 안다" 직후 인프라를 미룸 | 자기 논지와 충돌 |

### 3.3 되묻기

아래를 받으면 **즉시 멈추고 답만 한다.** 편집이나 추가 제안으로 넘어가지 않는다.

| 되묻기 | 응답 |
|---|---|
| "지금 필요한 논의야?" | §8의 2·3번으로 답한다. 못 답하면 철회 |
| "왜 해야 되는거야?" | 목표·제약과 연결한다. 일반론뿐이면 철회 |
| "이걸 ○○라고 불러?" | 분류를 다시 확인한다 |
| "대답만 해봐" | 도구를 쓰지 않는다 |

## 4. 구현 위치

| 루프 | 구현 | 실행 |
|---|---|---|
| L1 린트·포맷 | `backend/pyproject.toml` `[tool.ruff]` | `make fmt` · `make lint` |
| L2 계층 규칙 | `backend/pyproject.toml` `[tool.importlinter]` | `make arch` |
| L2 단위 테스트 | `backend/tests/unit/` | `make test` |
| L3 CI | `.github/workflows/backend.yml` | PR |
| L4 토큰 예산 | `.claude/hooks/check_doc_budget.py` | 편집 훅 · CI |
| L5 문서 동반 변경 | `.claude/doc-map.json` · `.claude/hooks/check_doc_sync.py` | `make doc-sync` (`check`에 포함) |
| L10 문서 라우팅 | `.claude/settings.json` PreToolUse `if` · `hooks/require-doc.sh` · `hooks/mark-doc-read.sh` | 자동 (편집 시도 시) |
| 편집 직후 | `.claude/hooks/on-edit.sh` | 자동 (L1·L2·L4를 함께 실행) |

**어느 코드가 어느 문서에 묶이는지는 `.claude/doc-map.json` 하나가 원천이다.** `AGENTS.md §5`의 "정보 → 단일 원천" 표를 경로로 옮긴 것이다. 이 파일과 `settings.json`이 어긋나면 편집 차단이 조용히 발화하지 않으므로, `make doc-sync`가 둘의 일치를 먼저 검사한다.

**규칙은 문서가 아니라 계약으로 존재한다.** `AGENTS.md §2.1`의 계층 규칙은 `backend/pyproject.toml`의 import-linter 계약이 강제하고, `§3` 컨벤션은 ruff 규칙이 강제한다. 문장만 고치고 계약을 안 고치면 아무것도 바뀌지 않는다.

새 루프를 추가하면 **이 문서의 §2 표와 실제 구현을 같은 커밋에서 갱신한다.**
